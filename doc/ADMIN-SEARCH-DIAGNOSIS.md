# 관리자 검색 재조회 진단

## 결론

관리자 검색 버튼은 입력 상태만 바꾸는 클라이언트 이벤트가 아니라 기본 HTML `GET` 폼 제출을 수행한다. 따라서 검색할 때마다 `/admin?q=검색어`로 새 요청이 발생하고, 서버 컴포넌트가 다시 렌더링된다.

## 호출 흐름

1. `widgets/admin-dashboard/ui/admin-dashboard.tsx`의 검색 폼이 `action="/admin"`, `method="get"`으로 선언되어 있다.
2. 폼에 검색용 `onSubmit`과 `preventDefault()`가 없으므로 브라우저가 기본 문서 이동을 실행한다.
3. `app/admin/page.tsx`가 변경된 `searchParams`를 읽어 `getAdminRestaurantPage()`를 다시 호출한다.
4. `getAdminRestaurantPage()`는 검색 결과만 조회하지 않고 전체 통계, 공개 수, 방문 여부별 수, 이미지 누락 수, 필터 결과 수, 카테고리 목록, 현재 페이지 목록을 다시 조회한다.

## 현재 요청 비용

검색 한 번마다 맛집 관련 Supabase 요청이 최소 8개 발생한다.

- 전체 맛집 수
- 공개 맛집 수
- 방문한 맛집 수
- 미방문 맛집 수
- 이미지 누락 맛집 수
- 검색 필터 결과 수
- 카테고리 목록
- 현재 페이지의 맛집 목록

Supabase가 설정된 환경에서는 `proxy.ts`와 `requireAdmin()`의 인증 확인도 요청에 포함된다.

## 의도된 동작과 불편한 점

현재 관리자 목록은 페이지네이션과 서버 검색을 사용하므로 DB에서 검색하는 구조 자체는 타당하다. 다만 기본 GET 제출이라 브라우저 관점에서는 전체 페이지를 새로 불러오는 것처럼 보이고, 검색과 무관한 통계 쿼리까지 매번 반복된다.

## 개선 방향

- 검색 버튼 제출 시 `router.replace()`를 사용해 전체 문서 새로고침 대신 App Router 전환으로 처리한다.
- 검색 중에는 목록 요청만 수행하고, 전체 통계·카테고리 데이터는 별도 캐시 또는 초기 로드 데이터로 재사용한다.
- 데이터 규모가 작을 때만 전체 관리자 데이터를 한 번 받아 클라이언트 필터링으로 전환한다. 데이터가 늘어날 경우 현재의 서버 페이지네이션을 유지하는 편이 안전하다.

## 적용한 수정

검색 폼을 일반 HTML `form`에서 Next.js `Form` 컴포넌트로 변경했다. 이제 검색어와 필터는 동일하게 `/admin`의 검색 파라미터로 전달되지만, 브라우저 전체 문서 새로고침 대신 App Router 클라이언트 전환으로 처리된다. `replace`와 `scroll={false}`를 사용해 검색할 때 방문 기록이 불필요하게 쌓이거나 목록 스크롤이 위로 이동하지 않도록 했다.

검색 결과를 서버 페이지네이션으로 가져오는 요청 자체는 남아 있다. 이는 전체 데이터를 브라우저에 미리 내려받지 않기 위한 의도된 동작이다.
